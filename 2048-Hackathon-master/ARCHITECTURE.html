2048 — Beginner's Codebase Guide

A plain-English walkthrough of what the game does, how the files fit together, how a key press moves tiles, and how the layout adapts to mobile.

1. What Is This Project?

2048 is a browser puzzle game. You slide numbered tiles on a 4×4 grid. When two tiles with the same number collide, they merge into one tile with double the value. The goal is to create a tile that reads 2048.

The entire game runs in a single HTML file with no server, no framework, and no build step needed to play it — just open index.html in a browser. The JavaScript uses the old-school constructor function + prototype style (pre-ES6 classes), which was the standard way to write object-oriented JS at the time this was built.

Key insight: There is no DOM-based game loop. The grid is only re-rendered when something actually changes (a move, restart, or win/lose). This keeps things simple and fast.

GameManager is the hub. Its four collaborators are passed in as constructor arguments — a simple form of dependency injection that makes each piece independently testable and swappable.

3. How a Key Press Moves the Tiles

Nine distinct things happen in sequence from the moment your finger leaves a key to the moment the tiles finish sliding on screen.

1
Key press captured — keyboard_input_manager.js A keydown listener on document checks a lookup table that maps raw key codes to direction integers (0 = Up, 1 = Right, 2 = Down, 3 = Left). Arrow keys, WASD, and Vim hjkl keys are all supported. If no modifier key (Ctrl, Alt, etc.) is held, event.preventDefault() stops the page from scrolling and emit("move", direction) fires.

Touch swipes follow the same path — touchstart records the start coordinates, touchend computes the delta, and the dominant axis determines the direction.
2
Event reaches GameManager — game_manager.js During construction, GameManager registered a listener: inputManager.on("move", this.move.bind(this)). The emit() call in step 1 iterates its stored callbacks array and calls GameManager.move(direction).
3
Guard check if (this.isGameTerminated()) return; — if the game is already won or lost and the player hasn't opted to keep going, the move is silently ignored.
4
Direction → movement vector getVector(direction) converts the integer to an {x, y} delta used to step across the grid: e.g. Left = {x: -1, y: 0}, Down = {x: 0, y: 1}.
5
Traversal order calculated buildTraversals(vector) decides the order to visit cells. The critical rule: process tiles starting from the edge they're moving toward, otherwise a tile would be checked before its destination is ready. Moving right? Process the rightmost column first. Moving down? Process the bottom row first.
6
Tile positions snapshotted prepareTiles() loops every cell, clears mergedFrom (no merges have happened yet this turn), and calls tile.savePosition() — copying the current {x, y} into tile.previousPosition so the renderer can animate from the old location.
7
Each tile is moved For every occupied cell (in traversal order):
  • findFarthestPosition() walks the tile step-by-step along the vector until it hits the grid edge or an occupied cell. Returns the last empty cell (farthest) and the first occupied cell beyond it (next).
  • If next has the same value and hasn't already merged this turn → merge: create a new tile at next with double the value, record mergedFrom, update the score, set won = true if the value hits 2048.
  • Otherwise → slide: move the tile to farthest with no merge.
8
Post-move bookkeeping Only if at least one tile moved: spawn a new random tile (90% chance of 2, 10% chance of 4); check if any moves remain (empty cells or adjacent matching tiles) — if not, over = true; call actuate() to save state and hand off to the renderer.
9
DOM updated — html_actuator.js Inside a requestAnimationFrame callback: the entire .tile-container is cleared and all tiles are re-rendered from scratch. Each tile's CSS class determines its visual position (tile-position-3-2 etc.). Moving tiles get their old position class set first, then a nested requestAnimationFrame swaps in the new position class — this triggers the CSS transition: transform 100ms that animates the slide. Merged tiles get a tile-merged bounce animation; new spawned tiles get a tile-new pop-in animation.

4. Styles and Mobile Layout

Design Tokens

All sizing flows from a small set of SCSS variables in style/main.scss. Tile size is always computed mathematically — there are no hard-coded pixel values for individual tiles:

$field-width:    500px;
$grid-spacing:   15px;
$grid-row-cells: 4;

// Derived automatically:
$tile-size: ($field-width - $grid-spacing * ($grid-row-cells + 1)) / $grid-row-cells;
// → (500 - 75) / 4 = 106.25px per tile

The game-field Mixin — The Responsive Trick

The entire board layout (game container, grid cells, tile position classes) is wrapped in a single @mixin game-field. This mixin uses whatever the variables are at the time it is called. It's called twice:

Desktop (default)

  • Called at the top level
  • Uses $field-width: 500px
  • Tile size ≈ 106px
  • Grid spacing: 15px

Mobile (< 520px)

  • Variables redefined to smaller values
  • Then @include game-field called again
  • Uses $field-width: 280px
  • Tile size ≈ 57px, spacing: 10px

The breakpoint is 520px ($field-width + 20px), triggered by @media screen and (max-width: 520px).

Tile Positioning (No top/left)

All tiles sit at position: absolute at the top-left corner of the tile container. They are moved using CSS transform: translate(x, y). The SCSS build loop generates all 16 position classes at compile time:

// Generated at build time for every grid cell:
.tile-position-3-2 {
  transform: translate(242px, 121px);  /* desktop */
}

When JavaScript swaps the position class on a tile element, the CSS transition: transform 100ms ease-in-out automatically animates the slide — no JS animation code needed at all.

Tile Color System

Tile colors are generated by a @while loop at compile time — no runtime JS involved. Each of the 11 tile values (2 through 2048) gets:

  • A base color linearly interpolated from cream (#eee4da) to gold (#edc22e) as the value increases
  • An optional override color for values 8–64 (oranges and reds)
  • A growing gold glow (box-shadow) on tiles 32 and above
  • Text color switches from dark brown to off-white on tile 8 and above
  • Progressively smaller font sizes for 3-digit and 4-digit numbers, with extra reductions on mobile
